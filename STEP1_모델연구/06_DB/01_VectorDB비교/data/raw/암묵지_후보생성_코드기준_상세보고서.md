## 1. 입력 전처리: LLM에 들어가기 직전까지

### 1-1. 이 단계에 도착하는 파일과 JSON 구조

STEP5 진입점(`step5_runner.py:38-42`, `Step5Runner.run`)이 파일 4개를 읽는다. 로드는 전부 `tacit_common/artifacts.py`의 전용 함수를 거친다(형식 어긋남 방지 원칙).

**(a) STT transcript** — `STEP3_전처리/transcripts/<video_id>.json`
`artifacts.load_transcript()`(`artifacts.py:65-68`)가 `Transcript` 모델(`intermediate.py:121-127`)로 검증하며 읽는다. 실제 파일(CLIP4) 구조:

```json
{
  "video_id": "CLIP4_재부팅및BIOS.mp4",
  "language": "ko",
  "model": "mobiuslabsgmbh/faster-whisper-large-v3-turbo",
  "utterances": [
    {"start": 22.48, "end": 24.6,
     "raw_text": "됐습니다. 화면이 나왔습니다.",
     "normalized_text": "됐습니다. 화면이 나왔습니다.",
     "repeat_hallucination": false}
  ]
}
```

발화 1건 = `Utterance`(`intermediate.py:106-119`): `start`/`end`(초, float, 원본 시간축), `raw_text`(STT 원문 — "절대 손실 금지" 주석), `normalized_text`(용어 정규화본), `repeat_hallucination`(Whisper 끝부분 환각 의심 플래그 — 삭제하지 않고 플래그만).

**(b) VLM 관찰** — `STEP4_YOLO_VLM관찰/output/vlm_observations/<video_id>.observations.json`
`load_observations()`(`artifacts.py:117-121`)가 `ActionDescription` 리스트로 읽는다(`intermediate.py:130-148`). 필드: `timestamp`(초 — 프레임 샘플링이 부여, VLM이 재계산 안 함), `actor`("오른손"/"시선" 등), `action`(관찰 문장), `objects`(보이는 YOLO 클래스명), `end_timestamp`+`repeat_count`(동일 문장 반복 관찰을 접은 압축 필드), `chunk`.

**(c) YOLO 검출** — `<video_id>.json`, `Detection` 리스트(`intermediate.py:88-96`): `timestamp`, `frame_idx`, `cls`, `conf`, `bbox`.

**(d) 프레임 메타** — `frames_meta.json`(영상 길이 `duration`, `fps` 조회용).

### 1-2. 가공 단계 — 텍스트가 "통으로" 들어가지 않는다

LLM 입력 직전까지 3단계 가공을 거친다:

**① 윈도우 묶기(코드)** — `Step5Runner.run`(`step5_runner.py:46`)이 `aligner.align(actions, transcript, flat_dets)` 호출 → `AlignedWindow` 리스트. 상세는 §2. 결과는 `output/aligned_windows/<video_id>.windows.json`으로 먼저 저장된다(`step5_runner.py:47`) — LLM에 뭐가 들어갔는지 나중에 파일로 추적 가능.

**② 윈도우 직렬화(코드)** — `QwenLLMFusion._serialize()`(`llm_fusion.py:187-221`). 윈도우마다 dict 하나:

- `window_id`: 순번 1-base → `"W01"` 형식(`_window_id`, `llm_fusion.py:182-185`). **직렬화와 재조립이 같은 규칙을 공유** — 이 ID가 나중에 후보를 윈도우에 결박하는 열쇠다.
- `case`: `fusion`/`action_only`/`utterance_only`(§3).
- `window_start`/`window_end`: `seconds_to_hhmmss()`로 "HH:MM:SS" 변환.
- `actions[]`: `timestamp`, `actor`, `action`, `objects_visible` + 반복 접힘이 있을 때만 `repeat_count`/`repeat_until`(`llm_fusion.py:196-206`).
- `utterances[]`: `timestamp`, `raw_text`, `repeat_hallucination`(`llm_fusion.py:208-218`).

**이 직렬화에서 걸러지는 것(입력 다이어트):**
- `normalized_text` **미전송** — raw_text와 거의 같은 문장 2벌을 보내 프롬프트만 키우던 것을 2026-07-06 제거(`llm_fusion.py:212-214` 주석: CLIP4 6,330토큰 prefill OOM의 일부 원인).
- **YOLO `detections` 미전송** — `AlignedWindow.detections`에 붙어 있고 windows.json에도 저장되지만, `_serialize()`가 만드는 payload에 아예 없다(actions/utterances만). `llm_fusion.py` 전체에 `detections` 참조가 0건임을 grep으로 확인. (§3-3, §8-4 참고)
- `chunk`, `end_timestamp`(raw), 기타 내부 필드 미전송.

**③ 메시지 조립(코드)** — `build_fusion_messages()`(`llm_fusion_prompt.py:187-208`): system(고정 프롬프트) + user(video_id + 윈도우 개수 + **compact JSON**) 2메시지. JSON은 `separators=(',', ':')`로 들여쓰기 없이 직렬화 — 들여쓰기 공백만으로 ~900토큰이 커져 OOM 문턱을 넘던 것을 압축(`llm_fusion_prompt.py:201-203` 주석).

### 1-3. 실제 조립된 프롬프트 예시 (실행으로 확인)

실제 산출물 `output/aligned_windows_motion_obs/CLIP4_재부팅및BIOS.mp4.windows.json`(윈도우 9개)을 `_serialize()`+`build_fusion_messages()`에 그대로 통과시켜 얻은 **실제 조립 결과**다(system 6,112자 / user 4,214자):

**system 메시지** = `FUSION_SYSTEM_PROMPT`(`llm_fusion_prompt.py:47-184`) 전문. 핵심 구성: 역할 선언("암묵지 후보를 서술하는 정제 도우미 — 판별은 다음 단계 몫") → ★★후보 단위 규칙(후보 1건=윈도우 1개, 전수 귀속, 인접 2개까지만 병합) → "너는 서술만 쓴다"(시각·원문은 시스템이 채움) → LED 진단 코드표 → 절대 규칙(할루시네이션 금지 5개조) → 접지 규칙 → 침묵 암묵지 요령 → 출력 견본 JSON.

## 2. 타임스탬프 윈도우 묶기

### 2-1. 파라미터 전부와 정의 위치

| 파라미터 | 값 | 코드 기본값 위치 | 실제 실행값 위치 |
|---|---|---|---|
| `window_sec` (행동 앵커 ± 허용 오차) | **4.0초** (즉 ±4초, 윈도우 기본 폭 8초) | `aligner.py:32` (`WindowAligner.__init__`) | `파이프라인_통합실행/config.yaml` `aligner.params.window_sec: 4.0` |
| `merge_overlapping` (겹침 병합) | **true** | `aligner.py:32` | config.yaml 동일 |
| `merge_cap_sec` (병합 후 최대 길이) | **20.0초** | `aligner.py:33` | config.yaml `merge_cap_sec: 20.0` |

`merge_cap_sec`은 2026-07-06 추가 — 상한 없이 겹치면 무조건 병합하던 구버전에서 클립 전체(-2~194초)가 윈도우 1개로 도미노 병합돼 LLM 입력이 폭발(OOM)한 사고의 재발 방지(`aligner.py:36-40` 주석).

이 값들은 `config.yaml → tacit_common/config.py(ComponentConfig) → step5_registry.build_aligner()`(`step5_registry.py:29-30`)를 거쳐 생성자 인자로 주입된다.

### 2-2. 매칭 로직 (의사코드) — `WindowAligner.align()` (`aligner.py:42-92`)

```
입력: actions(VLM 관찰), transcript(발화), detections(YOLO)

1) 행동 앵커 윈도우 생성 — 행동을 시각순으로 돌며:
   t0 = max(0, action.timestamp - 4.0)     # 음수 클램프(aligner.py:57, 2026-07-10)
   t1 = action.timestamp + 4.0
   이 [t0, t1] 구간과 "겹치는" 발화 전부 수거:
       겹침 판정 _overlaps(u.start, u.end, t0, t1) = (u.start <= t1 and t0 <= u.end)
       (aligner.py:94-96 — 발화 구간과 윈도우 구간의 구간-구간 겹침)
   수거된 발화 인덱스는 used_utt에 기록
   detections 중 t0 <= d.timestamp <= t1 인 것도 수거
   → AlignedWindow(t0, t1, actions=[그 행동 1개], utterances, detections)

2) 어느 행동 윈도우에도 안 걸린 발화(leftover) → 발화 자신의 [start, end]를
   구간으로 하는 utterance_only 윈도우로 별도 수거 (aligner.py:76-87)
   ← "발화만 있는 암묵지(케이스3)"를 잃지 않기 위한 장치

3) window_start 기준 정렬 (aligner.py:89)

4) 겹침 병합 _merge (aligner.py:98-119):
   for w in windows[1:]:
       overlap = w.window_start <= last.window_end
       capped  = (병합 후 전체 길이) <= 20.0초
       if overlap and capped:
           last에 흡수 (actions extend, 발화는 (start,end)로 dedup,
                        검출은 (frame_idx,cls)로 dedup)
       else:
           새 윈도우로 분리
```

같은 발화가 여러 행동 윈도우에 걸릴 수 있고(±창 겹침), 이 중복은 병합 시(`_extend_unique_utt`, `aligner.py:121-127`)와 LLM 출력 재조립 시(`llm_fusion.py:521-534`, `seen_utt`) 두 번 dedup된다.

### 2-3. 코드가 하나, 프롬프트가 하나 — 명확한 구분

- **윈도우 묶기 자체는 100% 코드**다(`aligner.py` — 모듈 docstring: "이 모듈은 모델을 안 쓴다(순수 로직)"). LLM은 이미 묶인 윈도우를 받을 뿐이다.
- LLM에게 허용된 유일한 "묶기 재량"은 **후보 레벨의 인접 윈도우 2개 병합 선언**(`window_ids: ["W03","W04"]`)이다. 이건 프롬프트 규칙(`llm_fusion_prompt.py:52-59`)으로 지시하되, 위반은 코드 게이트 `_check_window_binding()`(`llm_fusion.py:447-484`)이 하드 검사한다: 3개 이상 병합 → 실패, 비인접(순번 비연속) 병합 → 실패.

## 3. 케이스 분류 (A: 행동+발화 / B: 행동만 / C: 발화만)

### 3-1. 판정 주체: 코드다 (프롬프트 아님)

**윈도우 레벨** — `AlignedWindow.case` 프로퍼티(`intermediate.py:163-174`)가 결정적으로 계산:

```python
@property
def case(self) -> str:
    has_a = bool(self.actions); has_u = bool(self.utterances)
    if has_a and has_u: return "fusion"        # A: 행동+발화
    if has_a:           return "action_only"    # B: 행동만
    if has_u:           return "utterance_only"  # C: 발화만
    return "empty"
```

이 값이 직렬화 payload의 `"case"` 필드로 LLM에 **전달**된다(`llm_fusion.py:193`). 즉 LLM은 케이스를 판정하지 않고 통보받는다.

**후보 레벨** — 최종 후보의 `case` 필드도 코드가 유도(`llm_fusion.py:562-572`): 멤버 윈도우 case 집합에서 `fusion` 포함 또는 `action_only`+`utterance_only` 혼재 → `"both"`, 전부 utterance_only → `"utterance"`, 전부 action_only → `"action"`. 주석 명시: "LLM 출력과 무관한 결정적 값"(GT 조건 분포 대조용, 2026-07-09 추가).

### 3-2. 케이스별 출력 JSON 차이 — 전부 코드(`_rebuild_from_draft`)가 만든다

`llm_fusion.py:501-604`. 후보에 귀속된 윈도우(들)의 행동·발화를 시간순으로 섞어 `diagnostic_steps`를 생성:

| | 행동 이벤트 | 발화 이벤트 |
|---|---|---|
| `action` | VLM 관찰문 **원문** | `"(발화) <raw_text 원문>"` (`llm_fusion.py:552`) |
| `evidence` | `"action_only"` | `"utterance"` |
| `source_utterance` | `None` | raw_text **원문** |
| `timestamp` | 행동 관찰 시각 | **발화 시작 시각**(`round()` 후 HH:MM:SS — STEP6 transcript와 초 단위 일치, `llm_fusion.py:546-549`) |
| `utterance_timestamp` | 없음(None) | timestamp와 동일값(행동/발화 시각 혼입 회귀 검출용 별도 키) |

케이스별 상위 필드:
- **C(발화만)·A(둘 다)**: 그 후보 윈도우의 발화 시각들이 `situation_source`에 들어가고, `reasoning_origin=utterance`일 때만 같은 시각들이 `reasoning_source`에 들어간다(`llm_fusion.py:582-585`).
- **B(행동만)**: `situation_source=[]`, `source_utterance` 전부 None. **LLM이 `reasoning_origin="utterance"`를 달아도 코드가 `model_inferred`로 강제 교정**(`llm_fusion.py:556-560` — "위장 차단" 로그 출력). 프롬프트도 같은 내용을 지시하지만(`llm_fusion_prompt.py:91-92`) 최종 보증은 코드다.

### 3-3. YOLO 백업 그물 — **코드에 없음 (설계 문서에만 있음 / 미구현)**

"YOLO가 손-부품 접촉을 잡았는데 VLM 관찰이 없는 구간을 백업으로 살리는" 장치는 **현재 코드 어디에도 없다.** 확인 근거:

- `llm_fusion.py`에 `detections` 참조 0건(grep 확인). `_serialize()`는 actions/utterances만 payload에 넣는다.
- `AlignedWindow.detections`는 윈도우에 붙어 저장까지는 되지만(주석: "위치 힌트(코드레벨 판단용)", `intermediate.py:161`) 소비하는 코드가 STEP5에 없다.
- 문서 스스로 미구현이라고 기록: `docs/_archive_세션기록/_파이프라인_현황보고서.md:111` "**YOLO 백업그물** — 손-부품 접촉 이벤트 저장 + 융합 입력에 주입. **미반영**", `docs/_archive_세션기록/_배턴터치_이어서.md:44` "갭 B(`yolo_contacts` 백업그물) **미착수**".
- YOLO 검출이 실제로 쓰이는 곳은 STEP4 내부다: VLM 프롬프트에 구간별 실검출 클래스명을 주입하는 `part_injection`(`STEP4.../vlm_qwen.py:450-456`, config `vlm.params.part_injection: true`). 이건 "백업 그물"이 아니라 VLM 관찰의 보조 정보다.

## 4. 출력 JSON 스키마 전체 해부 (`step5_schema/tacit_schema.py`)

`SCHEMA_VERSION = "1.4"`(`tacit_schema.py:23`). 파일 단위 출력은 `TacitKnowledgeDocument`(`tacit_schema.py:193-201`): `{schema_version, video_id, candidates:[...]}`.

**중요한 구조적 사실:** LLM이 직접 출력하는 것은 최종 스키마가 아니라 **초안 스키마 `FusionDraft`**(`tacit_schema.py:236-239`)다. 최종 `TacitKnowledgeCandidate`는 코드(`_rebuild_from_draft`)가 초안+윈도우 데이터로 조립한다. 아래 표의 "채우는 주체"는 이 구분을 반영한다.

### 4-1. 후보(TacitKnowledgeCandidate, `tacit_schema.py:110-127`) 전 필드

| 키 | 타입 | 의미 | 채우는 주체 |
|---|---|---|---|
| `id` | str | `tk_<video_stem>_<NNN>` 일련번호 | **코드** — `_assign_ids`(`llm_fusion.py:839-845`) 후 러너 `_finalize_metadata`(`step5_runner.py:87`)가 최종 덮어씀 |
| `schema_version` | str | "1.4" | **코드** — Pydantic 기본값(`tacit_schema.py:117`). 실제 산출물에서 "1.4" 확인 |
| `window_ids` | List[str] | 이 후보가 귀속된 윈도우(결박) | **LLM 선언**(초안의 유일한 구조 재량) + **코드 게이트 검증** |
| `case` | str/null | both/utterance/action | **코드** 유도(`llm_fusion.py:562-572`) — LLM 무관 |
| `metadata` | Metadata | 아래 4-2 | 혼합(아래) |
| `knowledge` | Knowledge | 아래 4-3 | 혼합(아래) |

### 4-2. metadata (Metadata, `tacit_schema.py:65-71` / Source `54-63`)

| 키 | 타입 | 의미 | 채우는 주체 |
|---|---|---|---|
| `scenario_id` | str | 원본 파일명 stem | **코드** (`step5_runner.py:88`) |
| `equipment` | str/null | 장비명 | **코드** — `config.yaml`의 `equipment: "Dell Precision 7920"`을 그대로 (`step5_runner.py:89`). 주석: LLM이 추측하면 None이 남아 STEP6 Gate A 쿼리에 "None"이 박히는 사고(2026-07-04)가 있어 코드가 강제 |
| `task` | str/null | 작업유형 | **LLM** (초안 metadata → `_rebuild_from_draft`가 `metadata=dc.metadata`로 통과, `llm_fusion.py:577`) |
| `keywords` | List[str] | 검색용 핵심어 3~6개 | **LLM** (프롬프트 지시 `llm_fusion_prompt.py:137-139`) |
| `scenario_title` | str/null | 이 후보 지식의 제목 | **LLM** (프롬프트: "클립 전체의 요약이 아니다") |
| `source.video_id` | str | 원본 파일명 | **코드** (`step5_runner.py:91`) |
| `source.clip_start` | str/null | "00:00:00" 고정 | **코드** (`step5_runner.py:93`) |
| `source.clip_end` | str/null | 영상 길이(frames_meta duration) | **코드** (`step5_runner.py:84,94`) |
| `source.transcript_ref` | str/null | transcript 파일 상대경로 | **코드** (`step5_runner.py:83,92`) |

프롬프트가 LLM에게 metadata 중 id/scenario_id/equipment/source를 "아예 쓰지 마라"고 지시하고(`llm_fusion_prompt.py:140-141`), 써도 러너가 덮어쓴다(`step5_runner.py:78-80` 주석: "LLM 출력을 신뢰하지 않고 여기서 덮어쓴다").

### 4-3. knowledge (Knowledge, `tacit_schema.py:94-107`)

| 키 | 타입 | 의미 | 채우는 주체 |
|---|---|---|---|
| `conflict` | bool | 본 것(VLM)과 들은 것(STT)의 내용 충돌 | **LLM**(Pass 1 초안, `DraftKnowledge.conflict`) — Pass 2 병합 시엔 **코드가 멤버 OR 승계**(`llm_fusion.py:742`) |
| `conflict_detail` | str/null | 충돌 내용 | **LLM**(Pass 1) / Pass 2 병합 시 코드가 멤버 것을 " / "로 연결(`llm_fusion.py:743-745`) |
| `situation` | str | 그 구간의 상황 서술 | **LLM** |
| `situation_source` | List[str] | 근거 발화 시각들("HH:MM:SS") | **코드** — 그 후보 윈도우의 (환각 아닌) 발화 시작 시각 전부(`llm_fusion.py:582`) |
| `tacit_insight` | str | 핵심 노하우 한 문장 | **LLM** |
| `reasoning` | str/null | 왜 그렇게 하는가 | **LLM** |
| `reasoning_source` | List[str] | reasoning 근거 발화 시각 | **코드** — `reasoning_origin=utterance`일 때만 발화 시각 복사, 아니면 `[]`(`llm_fusion.py:585`) |
| `reasoning_origin` | enum | `utterance` \| `model_inferred` | **LLM 선언 + 코드 강제 교정 3곳**(발화 0건 후보 `llm_fusion.py:556-560`, 접지 무접점 재시도 소진 시 `:355-359`, Pass 2 위장 병합 `:750-753`) |
| `diagnostic_steps` | List[DiagnosticStep] | 시간순 행동/발화 스텝 | **코드 전체 생성**(`llm_fusion.py:537-554`) — LLM이 출력해도 버려짐(초안 스키마에 이 필드가 없어 Pydantic이 무시, `llm_fusion.py:490-491` 주석) |

DiagnosticStep 하위 키(order/action/evidence/source_utterance/timestamp/utterance_timestamp)는 §3-2 표 참조 — **전부 코드가 채운다**(스키마 주석 `tacit_schema.py:82-88`의 `[자동]` 표기와 일치).

### 4-4. 특별 확인 요청 항목

- **`schema_version`**: 코드에 반영돼 있음. 정의 `tacit_schema.py:23`, 후보와 문서 양쪽에 기본값으로 박히고(`:117`, `:199`), 실제 산출물 `CLIP4_재부팅및BIOS.mp4.tacit.json`에서 `"schema_version": "1.4"` 확인.
- **`conflict`/`conflict_detail`**: 코드에 반영돼 있음. 스키마(`tacit_schema.py:97-98`), LLM 초안 스키마(`:224-225`), 프롬프트 규칙 5(`llm_fusion_prompt.py:93-99` — "둘 다 남기고 conflict=true, 어느 쪽이 맞는지 판단하지 마라"), 재조립 통과(`llm_fusion.py:579-580`), Pass 2 OR 승계(`:742-745`), cross_check 경고("conflict=true인데 detail 비었음", `tacit_schema.py:189-190`)까지 일관 구현. 단, "conflict가 true인 후보를 코드가 별도 검증/대조"하는 로직은 없음 — 진위 판별은 설계상 STEP6 몫.
- **`keywords`/`task`**: 순수 LLM 생성(입력에서 복사되는 값 아님). **`equipment`**: 순수 코드(config 상수).

### 5-2. "timestamp가 실제 transcript에 존재하는지 확인"의 실제 위치

- **STEP5 안에서는 별도 대조 검증이 없다 — 필요가 없게 설계됐기 때문이다.** 1.4 재설계에서 utterance 스텝의 timestamp/source_utterance는 LLM이 아니라 코드가 transcript 원본(윈도우에 담긴 Utterance 객체)에서 직접 채우므로(`llm_fusion.py:546-554`), **구성상(by construction) 항상 transcript에 실존**한다. LLM 창작이 끼어들 자리가 제거됐다.
- 실제 "transcript 실존 대조"는 **다음 단계(STEP6)의 0단계(timestamp_validity)**가 수행하며, STEP5 쪽에서는 `step6_adapter.py`가 그 대조가 어긋나지 않도록 형식 변환을 책임진다: 발화 시각을 `round()`로 STEP5와 동일하게 변환하고(`step6_adapter.py:33-41`), 변환 후 건수/원문/시각을 원본과 전수 대조해 하나라도 다르면 예외로 죽는다(`:76-94`), 경계 겹침으로 인한 false reject도 어댑터가 보정한다(`:59-74`).
- 참고: 구버전 흔적으로 `cross_check`의 ⓓ(발화 원문 대조)가 남아 있어 원문 레벨 대조는 경고로 한 번 더 돈다(현 구조에선 항상 통과해야 정상).

### 5-3. 검증 실패 시 처리 (재시도 정책)

`fuse()` 재시도 루프(`llm_fusion.py:311-404`):
- 시도 예산: `max_retries` — 코드 기본 2(총 3회, `:45`), **실제 config는 5(총 6회)**(`config.yaml llm.params.max_retries: 5`, 주석: 잡 2265/2267 실측으로 증액).
- 실패 시 짧은 **피드백 메시지**를 대화에 붙여 재생성(`:393-402`) — 직전 출력 전문은 echo하지 않음(prefill OOM 방지, 실측 근거 주석).
- **OOM이면 누적 피드백을 버리고 원본 메시지로 리셋**(`:376-382`) + gc/empty_cache(`:371-375`).
- 온도는 전 시도 0.2 고정 — 구정책(0.2→0.45→0.7 상승)은 접지 붕괴를 유발해 2026-07-08 폐지(`:312-317` 주석). ※ config.yaml의 max_retries 주석에 "온도 스케줄 0.7 상한 유지"라는 낡은 문구가 남아있으나 코드는 고정이다(§8-7).
- 전부 소진: Pass 1은 `RuntimeError`로 **전체 실패**(후보 0건, `:404`) — 단 접지 위반(6번)만은 버리지 않고 강제 교정 후 통과. Pass 2는 실패해도 Pass 1 결과 반환(응집은 "개선이지 필수가 아님").

## 6. 할루시네이션 방지 장치 목록

### 6-1. 프롬프트 레벨 (`llm_fusion_prompt.py`, 유도 — 강제력 없음)

1. **절대 규칙 5개조**(`:85-99`): 입력에 없는 사실 생성 금지(수치·도구·안 한 말) / 묶기·분류·라벨링만 허용 / 발화 직접 도출만 `utterance` / 일반지식 추론은 `model_inferred` 정직 태깅, 위장 절대 금지 / 내용 충돌 시 둘 다 남기고 conflict=true(판단 금지).
2. **역할 축소 선언**(`:61-70`): "너는 서술만 쓴다 — diagnostic_steps·timestamp·source_utterance는 출력하지 마라, 써도 버려진다."
3. **접지 규칙**(`:101-110`, 2026-07-08): 발화가 있으면 발화의 '왜'를 먼저 찾아 그 표현을 살려 쓰고 utterance 태깅 — 반대 방향(안전한 일반론 도피) 차단. 하드 게이트는 일부러 안 둠("강제하면 위장을 유도한다", `:22`).
4. **발화 없는 윈도우 규칙**(`:91-92`): 근거 발화가 없으므로 origin은 반드시 model_inferred.
5. **repeat_count 오독 금지**(`:143-149`): 반복 관찰 병합 흔적을 "N회 반복 동작"의 근거로 쓰지 마라.
6. **LED 코드표 사용 규칙**(`:35-45`): 관찰에 없는 깜빡임 지어내기 금지, 발화 해석이 있으면 표보다 발화 우선.
7. **placeholder 금지**(`:131-133`): 견본 문장 베끼기·"..." 그대로 뱉기 실패 처리.
8. **insight≠reasoning**(`:121-125`): 같은 내용 복사 금지.
9. Pass 2(`llm_grouping_prompt.py:64-67`): 그룹 서술에 입력에 없는 사실 추가 금지, utterance 멤버 없으면 utterance 태깅 금지, 1건 그룹은 서술 echo 자체를 금지.

### 6-2. 코드 레벨 (강제)

1. **재조립 원천 차단** — 시각·발화 원문·스텝을 LLM 출력에서 안 받음(`_rebuild_from_draft`). 할루시네이션 가능 표면적을 서술 필드로 축소한 것이 1.4 재설계의 본질.
2. **reasoning_origin 강제 교정 3곳** — 발화 0건 후보(`llm_fusion.py:556-560`) / 접지 무접점 재시도 소진(`:355-359`) / Pass 2 위장 병합(`:750-753`).
3. **접지 게이트**(`_ungrounded_utterance_claims`) — "utterance라고 신고했지만 발화와 무접점"인 위장을 문자열 대조로 적발.
4. **발화 커버리지 게이트**(`_missing_utterances`) — 입력 발화를 통째로 버리는 탈선 적발(형식만 보던 합격 기준의 보강, 2026-07-06).
5. **윈도우 귀속 게이트**(`_check_window_binding`) — 클립 전체를 후보 1건으로 뭉치는 요약 탈선 적발.
6. **탈선 문자 게이트**(`_looks_derailed`) — 깨진 토큰 생성 즉시 폐기.
7. **cross_check 경고 6종**(§5-1 표 8행) — 관찰→발화 둔갑, 발화 지어냄 등.
8. **결정적 메타데이터 덮어쓰기**(`_finalize_metadata`) — id/scenario_id/equipment/source를 LLM 출력과 무관하게 코드 값으로.
9. **Pass 2 보수성** — 1건 그룹은 Pass 1 객체 재사용(바이트 동일 보장, `:738-739`), conflict는 코드 OR 승계, 발화 원문을 Pass 2 입력에 아예 안 줌("재창작할 재료를 안 준다", `:635-637`).
10. **Qwen3 thinking 차단**(`:115-123`) — `<think>` 블록의 JSON 오염을 로딩 시점에 차단(`enable_thinking=False` 주입).

## 8. 불일치 — 설계 문서/프롬프트 vs 실제 코드

1. **스키마 버전: 계획서 v1.3 vs 코드 v1.4.** 계획서 §5(`전처리_파이프라인_계획서.md:122-201`)는 v1.3 구조를 "그대로 따르라"고 하지만, 코드는 v1.4(`tacit_schema.py:23`)로 진화했다: 계획서에 없는 `window_ids`/`case`/`utterance_timestamp` 필드가 추가됐고, "LLM이 최종 스키마를 직접 출력"하던 구조가 "LLM은 초안(FusionDraft)만, 시각·원문은 코드 재조립"으로 바뀌었다(2026-07-08 재설계, `tacit_schema.py:204-216` 주석). 계획서 §5의 필드 채움 주체 표기(`[4 LLM]`이 diagnostic_steps 채움)도 현재는 코드 담당으로 바뀌어 낡았다.

2. **"근거성 발화 추출" 단계: 계획서에는 있고 코드에는 없음(의도적 폐기).** 계획서 §3-3(`:100-106`)은 정제 단계에서 정규식/LLM 분류기로 인과·조건·주의 발화를 추출하라고 하지만, 코드는 이를 폐기하고 raw 발화를 전부 LLM에 넘긴다. 폐기 기록: `intermediate.py:109-111` Utterance docstring "근거성 판단은 여기서 안 한다 → 융합 LLM이 raw 발화로 직접 (한국어 구어체 정규식 근거판단은 실측상 0건이라 폐기)". 프롬프트도 이를 반영: "발화의 근거성 판단은 전적으로 너의 몫이다. 앞단계는 발화를 거르지 않고 그대로 넘긴다"(`llm_fusion_prompt.py:76-79`).

3. **필드명 표기: 계획서 `reason_source` vs 코드 `reasoning_source`.** 계획서 §4(`:117`)는 "`reason_source` / `*_source`"라고 쓰지만 실제 키는 `reasoning_source`(`tacit_schema.py:103`)다(§5 예시 JSON에는 올바르게 적혀 있어 §4 본문만의 오기).

4. **YOLO 백업 그물: 문서상 "예정", 코드 미구현.** §3-3 참조. `docs/_archive_세션기록/_파이프라인_현황보고서.md:111`("미반영"), `docs/_archive_세션기록/_배턴터치_이어서.md:44`("미착수")가 스스로 인정. detections는 윈도우까지만 오고 LLM 입력·후보 생성에 전혀 쓰이지 않는다.

5. **프롬프트의 `source="human_observation"` / `chunk="out_of_coverage"` 규칙은 실제로 발동 불가능(죽은 규칙).** 프롬프트 `llm_fusion_prompt.py:151-155`는 이 표시가 있는 행동의 취급을 지시하지만, **그 필드는 LLM까지 도달하지 않는다**: ⓐ `ActionDescription`(`intermediate.py:130-148`)에 `source` 필드가 없어 Pydantic이 로드 시 조용히 버리고(실측: STEP4 모션O 관찰 JSON에 `"source": "human_observation"` 1건이 있으나, 그것이 흘러간 `aligned_windows_motion_obs/CLIP4....windows.json`에는 source 키가 0건 — 행동 문장 자체는 살아서 전달됨), ⓑ `chunk`는 모델 필드로는 존재하나 `_serialize()`(`llm_fusion.py:196-206`)가 payload에 넣지 않는다. 즉 사람 추가 관찰은 "일반 VLM 관찰과 구분 불가능한 형태"로 LLM에 들어간다 — 결과적 동작은 프롬프트 의도("동일하게 관측 사실로 취급")와 같지만, 규칙 자체는 코드상 트리거될 수 없다.

6. **이름의 화석들(동작에는 영향 없음).** ⓐ config `llm.impl: "qwen2_5_14b"`이지만 실제 모델은 `Qwen/Qwen3-14B`(2026-07-09 교체) — registry 키가 역사적 이름일 뿐 클래스는 모델 중립(config 주석에 명시). ⓑ `llm_fusion.py` 파일 헤더 docstring과 클래스 주석("Qwen2.5-14B 융합 어댑터"), 생성자 기본값(`model_name="Qwen/Qwen2.5-7B-Instruct-AWQ"`, `backend="vllm"`, `:37-38`)이 낡음 — 실행 시 config가 `Qwen3-14B`/`hf_transformers`/`nf4`로 전부 덮어써 실효 없음(CLAUDE.md도 "이 클러스터에서 vLLM 불가" 명시). ⓒ `vllm` 분기 코드(`_load` `:88-106`, `_infer` `:412-416`)는 남아 있으나 이 클러스터에서는 죽은 경로.

7. **config 주석의 온도 스케줄 문구 낡음.** `config.yaml`의 `max_retries: 5` 주석에 "온도 스케줄은 0.7 상한 유지"라고 남아 있으나, 코드는 2026-07-08 개정으로 전 시도 온도 0.2 고정이다(`llm_fusion.py:312-317` — 온도 상승이 접지 붕괴의 원인으로 실측 확정돼 폐지).

8. **계획서 §8의 "미해결 이슈"는 코드상 해결됨(문서 미갱신).** §8(`:239-261`)은 "evidence 태깅 정확도가 신뢰 못할 수준, 코드 레벨 규칙 보강 검토"를 미해결로 남겼는데, 바로 그 방향(1.4 재설계: evidence/timestamp를 LLM 자유 판단에서 코드 결정으로 이관)이 2026-07-08 구현 완료됐다. 계획서는 이 해결을 반영하지 않은 상태다.

## 부록: 발표 예상 질문 5개와 답

**Q1. "LLM이 타임스탬프를 지어내면 어떻게 막나요?"**
A. 막는 게 아니라 **받지를 않습니다.** v1.4 재설계(2026-07-08)에서 LLM 출력은 서술 초안(`FusionDraft`)뿐이고, `diagnostic_steps`의 timestamp·source_utterance는 코드(`_rebuild_from_draft`, `llm_fusion.py:501-604`)가 윈도우에 담긴 STT/VLM 원본 데이터에서 채웁니다. LLM이 timestamp를 출력해도 초안 스키마에 그 필드가 없어 Pydantic이 무시합니다. 그래서 시각은 구성상 항상 원본에 실존하고, STEP6 0단계의 transcript 대조를 통과할 수 있게 발화 시각 반올림 규칙(`round()`)까지 어댑터와 맞춰 놨습니다(`llm_fusion.py:546-549`).

**Q2. "행동과 발화를 왜 1:1 매칭하지 않고 ±4초 윈도우로 묶나요? 4초는 어디서 나온 값인가요?"**
A. 이 정비공은 말과 행동을 동시에 하지 않습니다(말 먼저/행동 먼저/무언 — `aligner.py:5` 및 프롬프트의 '지연 발화' 규칙). 그래서 1:1 매칭은 설계상 금지하고, 행동을 앵커로 ±`window_sec`(4.0초, `config.yaml aligner.params`) 안에 걸치는 발화를 '구간'으로 묶어 판단은 LLM에 맡깁니다. 어느 행동에도 안 걸린 발화는 utterance_only 윈도우로 따로 살려서(aligner.py:76-87) "발화만 있는 암묵지"를 잃지 않습니다. 겹치는 윈도우는 병합하되 20초 상한(`merge_cap_sec`)을 둬서 클립 전체가 한 윈도우로 뭉치던 OOM 사고를 막았습니다. 다만 수십 초 뒤에 설명이 오는 지연 발화는 4초 창 밖이라, 인접 윈도우 2개 병합(LLM 선언+코드 게이트 검증)으로 보완합니다.

**Q3. "reasoning_origin이 utterance라는 걸 어떻게 믿죠? LLM이 자기 추론을 발화 근거인 척할 수 있잖아요."**
A. 3중 방어입니다. ① 프롬프트에 위장 절대 금지 + 반대로 발화가 있으면 접지 우선 규칙(도피 방지). ② 코드 게이트 `_ungrounded_utterance_claims`(`llm_fusion.py:240-275`)가 utterance라고 신고된 reasoning을 그 윈도우의 실제 발화와 문자열 대조(따옴표 인용 4자+ 또는 정규화 6자 공통부분)해서 무접점이면 재시도시킵니다. ③ 발화가 0건인 윈도우의 utterance 신고는 무조건 `model_inferred`로 강제 교정합니다(`:556-560`). 재시도가 소진되면 후보를 버리는 대신 `model_inferred`로 정직 태깅해 통과시킵니다 — 후보를 잃는 것보다 정직한 라벨이 낫다는 설계입니다.

**Q4. "Pass 2(응집)에서 병합하면서 내용이 왜곡될 위험은요?"**
A. Pass 2는 실패해도 안전하게 설계했습니다. ① 1건 그룹(대부분)은 LLM 재서술 없이 Pass 1 객체를 그대로 씁니다 — 바이트 동일 보장(`llm_fusion.py:738-739`), 대조용 pass1.json도 남깁니다. ② 병합 그룹의 시각·발화·스텝은 코드가 멤버 윈도우 전체에서 재조립하고, conflict는 멤버 OR 승계, 발화 원문은 Pass 2 입력에 아예 안 줘서 재창작 재료를 차단합니다. ③ 비인접 병합·클립 전체 과잉병합은 코드 게이트가 반려하고, 전부 실패하면 Pass 1 결과를 그대로 냅니다("죽는 것보단 파편이 낫다", `:834-837`).

**Q5. "행동만 있고 발화가 없는 구간(침묵 암묵지)은 어떻게 처리되나요?"**
A. aligner가 그 행동을 앵커로 `action_only` 윈도우를 만들고(케이스 판정은 코드 — `AlignedWindow.case`), 프롬프트의 침묵 암묵지 규칙(`llm_fusion_prompt.py:112-119`)이 "숙련자는 하지만 초보자는 생략하는 비파괴적 확인 동작인지" 살펴 서술하게 합니다. 이때 reasoning은 발화 근거가 없으므로 반드시 `model_inferred`이고, 코드가 이를 강제합니다. 후보를 버리는 판단은 이 단계가 하지 않습니다 — "암묵지가 아니어 보여도 버리지 마라"가 프롬프트 첫 단락의 지시이고, 판별은 STEP6 몫입니다. (참고: STEP6에서 침묵 암묵지가 접지 점수에서 구조적으로 감점되는 이슈는 별도 협의 안건으로, 이 단계 코드 범위 밖입니다.)
