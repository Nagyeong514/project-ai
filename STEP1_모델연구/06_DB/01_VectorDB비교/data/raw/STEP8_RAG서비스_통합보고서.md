# STEP8_RAG서비스 통합 보고서

**작성일**: 2026-07-04
**대상**: 팀원 공유용 (STEP8_RAG서비스 폴더가 뭐고 왜 이렇게 만들어졌는지)
**실행법은 이 문서가 아니라 `STEP8_RAG서비스/README.md` 참고.** 이 문서는 배경·결정
근거·실측 결과 위주.

---

## 1. 배경 — 왜 두 폴더를 합쳤나

"STT로 질문 → 백엔드가 벡터검색 + LLM 답변생성 → TTS로 응답"하는 웹앱을 만드는 과정에서,
같은 목표(암묵지 RAG)를 서로 다른 팀원이 독립적으로 구현한 두 결과물이 있었다.

| | **STEP7_DB** (안나경) | **voice-rag-upload** (서시은) |
|---|---|---|
| 형태 | CLI 파이프라인 | FastAPI 웹서버 + 브라우저 UI |
| 강점 | 프리플라이트(무거운 모델 로드 전 5초 검증), pydantic config 검증, assert 스모크 테스트, timestamp 검증, accept/hold/reject 필터 훅 | Ollama LLM 자연어 답변, 환경변수 하이퍼파라미터 스위치, Recall@k 평가, embed-mode 비교 실험 구조 |
| 약점 | LLM 없음(템플릿 조립만), 하이퍼파라미터 코드에 고정 | 방어 로직 없음(프리플라이트/assert/pydantic 검증 부재), 환각 통제를 시스템 프롬프트에만 의존 |

두 결과물을 각각 쓰기보다, **"뼈대는 서시은, 안전장치는 안나경"** 원칙으로 하나로
합쳐 `STEP8_RAG서비스/`를 만들었다. 입력 데이터는 다른 파일럿 데이터를 새로 만들지 않고
STEP7_DB가 이미 갖고 있던 예시 JSON(`gold_records`, 9건)을 그대로 참조한다.

## 2. 통합 방식 — 파트별로 무엇을 가져왔나

### 파트1: JSON → 벡터DB 적재 (`ingest.py`)
서시은의 핵심 아이디어(`raw_json`을 통째로 payload에 저장해 LLM 컨텍스트로 재사용)는
그대로 유지했다. 여기에 안나경의 방어 로직 4가지를 이식했다:
- 무거운 임베딩 모델을 불러오기 전에 `preflight.py`로 필수 패키지/config/경로를 먼저 검증
- 스키마가 안 맞는 JSON은 죽지 않고 건너뛰며 경고만 남김(관용적 실패)
- `diagnostic_steps`의 timestamp가 clip 범위를 벗어나면 경고(적재는 계속 진행)
- 적재 후 `assert count > 0`으로 "에러 없이 끝남 = 성공"이라는 착각을 방지

### 파트2: RAG 검색 (`search.py`, `evaluate.py`)
서시은의 환경변수 스위치(`TOP_K`/`SIM_THRESHOLD`/`COLLECTION`/`EMBED_MODE`)와 Recall@k
평가 구조를 그대로 살렸다. 안나경의 `--accept_only` 필터 훅(routing==accept만 검색)을
Qdrant Filter로 이식했다. `evaluate.py`의 평가 질문 세트는 서시은 자신의 예시 3건 기준이던
것을 STEP7 gold_records 9건 기준으로 다시 작성했다 — tacit_insight를 그대로 베끼지 않고
신입이 실제로 물어볼 법한 증상 표현으로 썼다(예: "램 뺄 때 한쪽 래치만 눌러도 되나요?").

**실측 결과**: 9개 질문 전부 top1 정답 매칭(Recall@3 = 9/9). 덤으로 embed-mode를
`full`(상황+노하우+이유+절차+키워드)과 `insight`(노하우 단독)로 비교했더니 `full`이
9/9, `insight`가 8/9로 나왔다 — **STEP7_DB가 이전에 실측했던 결론("situation을 붙여야
증상 언어와 더 잘 붙는다")이 이 스택에서도 재현됨**을 확인했다.

### 파트3: LLM 답변 생성 (`app.py`)
서시은의 Ollama 기반 자연어 답변 생성을 그대로 쓰되, "이중 방어" 구조를 만들었다:
1. **방어선1(구조적)**: 검색 결과가 임계값 미만이면 `search.py`가 빈 리스트를 반환하고,
   `app.py`는 그 경우 **LLM을 아예 호출하지 않는다.**
2. **방어선2(프롬프트)**: 그래도 애매하게 통과한 경우를 위해 "검색된 근거만 사용, 부족하면
   부족하다고 말하라"는 시스템 프롬프트를 유지한다.

## 3. 실측 중 발견한 것들 (중요도순)

### 3-1. 유사도 임계값 0.35는 애매한 질의를 못 거른다 → 0.40으로 상향
서시은 원본 기본값(`SIM_THRESHOLD=0.35`)으로 "오늘 점심 뭐 먹지"를 질의했더니 top1
유사도가 0.372로 임계값을 통과해버렸다. 다행히 방어선2(시스템 프롬프트)가 "특별한 음식
정보는 제공 못한다"고 정직하게 답해 사고는 안 났지만, 이건 **방어선1이 뚫린 상태에서
방어선2가 운 좋게 막은 것**이지 구조적 보장이 아니었다.

STEP7_DB가 예전에 이미 같은 문제를 실측으로 검증해뒀다(무관 질의 baseline이 0.30~0.36대로
나와서 0.30으로는 안 걸러지고, 0.40에서 뚜렷한 갭이 있음을 확인). 그 값을 그대로 가져와
`SIM_THRESHOLD` 기본값을 0.40으로 올렸고, 재검증 결과 같은 질의가 이번엔 **방어선1에서
바로(0.47초 만에, LLM 호출 없이) 차단**되는 것을 확인했다.

**교훈**: 임계값은 감으로 정하지 말고, 무관한 질의군과 관련 질의군의 실측 유사도 분포
갭을 보고 정해야 한다. 두 프로젝트가 독립적으로 같은 함정(느슨한 임계값)에 빠졌다가
같은 방식(실측 갭 확인)으로 고쳐졌다는 것 자체가 이 원칙이 맞다는 방증이다.

### 3-2. 이 환경에 이미 Ollama가 깔려 있었다 (sudo 없이)
`team_a2` 계정 홈(`~/.local/ollama`)에 이미 Ollama가 설치돼 있고 `qwen2.5:14b-instruct`가
pull까지 되어 있었다. 실행 로그(`serve.log`)를 보면 2026-07-04 오전에 이미 누군가
(정황상 서시은) 같은 파이프라인을 이 환경에서 테스트해본 흔적이 있다. 앱 코드 기본값인
`qwen2.5:3b-instruct`는 없어서, 이미 받아져 있는 14b로 기본값을 바꿨다(3b를 쓰고 싶으면
`LLM_MODEL` 환경변수로 지정 가능).

### 3-3. Ollama는 GPU 노드에서 띄워야 한다 — 로그인 노드(CPU)는 비현실적
처음에 로그인 노드에서 그냥 Ollama를 띄웠더니 14b 모델 추론에 CPU로 2분 넘게 걸려
타임아웃이 났다(정상 요청이 실패로 보임). 이미 떠 있던 팀 공용 GPU 잡(RTX6000 x2, n5)에
`srun --overlap`으로 편승시켜 재기동하니 같은 요청이 **14초**로 끝났다. 추가로 기본
바인딩(`127.0.0.1`)은 그 GPU 노드 밖에서 접근이 안 돼 `OLLAMA_HOST=0.0.0.0`으로도
바꿔야 했다. (자세한 명령어는 README의 "1. Ollama 서버" 참고)

## 4. 최종 검증 결과 요약

| 테스트 | 결과 |
|---|---|
| 적재(9건) | `assert count>0` 통과, 스키마 불일치/timestamp 이상 파일도 안전하게 처리 확인 |
| Recall@3 (embed_mode=full) | 9/9 (1.00) |
| Recall@3 (embed_mode=insight) | 8/9 (0.89) — full 방식이 더 나음을 재확인 |
| 정상 질의 → LLM 답변 | 검색 근거만 사용, 형식(핵심→절차→출처) 준수, GPU로 14초 |
| 완전 무관 질의 | 방어선1이 즉시 차단(0.16~0.47초, LLM 호출 없음) |
| 애매한 질의("점심 뭐 먹지") | 임계값 0.40 적용 후 방어선1에서 바로 차단 (0.35였을 때는 방어선2가 겨우 막음) |

## 5. 현재 한계 / 다음에 할 일

- **입력 데이터가 실제 STEP3 산출물이 아니라 예시(gold_records 9건)** — STEP3 VLM이
  실제 데이터를 뽑을 수 있게 되면 `STEP8_RAG서비스/config.py`의 `input_dir`만 바꾸고
  재적재하면 된다(코드 변경 불필요).
- **Ollama가 팀 공용 GPU 잡에 임시로 편승 중** — 정식 서비스로 올리려면 이 프로젝트
  전용 GPU 할당이 필요하다.
- **voice-rag-upload의 ChromaDB 잔재(`inspect_db.py`, `knowledge_db/`)는 안 가져왔다** —
  실제 코드(Qdrant)와 안 맞는 이전 실험 흔적으로 판단해서 죽은 코드로 처리했다.
