# 실행 전 방어 체크리스트

> 2026-07-03, STEP6_품질검증에서 `langgraph` 미설치로 GPU 할당 시간을 날린 사건 이후 정리.
> 최근 3일 SLURM 잡 151개 중 FAILED 56건(exit 1이 46건)을 분석해서 나온 결론.

## 핵심 원칙 (이 한 줄이 전부)

> **무거운 거(모델 로드) 위로는 전부 5초 안에 죽을 수 있는 검증만, 무거운 거 아래로 내려간
> 에러만 진짜 GPU/로직 문제로 취급한다.**

이 한 줄이 exit code 원인 분류를 자동으로 해준다. "무거운 거 위"에서 죽으면 = 우리 실수(설정/경로/설치),
"무거운 거 아래"에서 죽으면 = 진짜 파봐야 하는 문제(OOM/로직버그).

## 왜 md만으로는 안 되는가

이 체크리스트를 문서로만 남기면 "읽고 고개 끄덕이지만 실제로는 안 지켜지는" 규칙이 된다.
그래서 각 프로젝트 폴더(예: `STEP6_품질검증/`)에 이 체크리스트를 **실제로 실행하는 코드**를
같이 둔다: `preflight.py`(1~4단계 실행) + `config.py`(pydantic으로 3단계 자동화).
`main.py`(또는 `run.py`)의 진입 함수 첫 줄에서 `run_preflight()`를 강제로 호출하게 만들어서,
사람이 체크리스트를 안 읽어도 코드가 대신 걸러주게 한다.

## 순서 (반드시 이 순서, 위에서부터)

**1. import 체크** ← 가장 먼저.
필수 패키지가 실제로 import되는지 `importlib.import_module()`로 확인한다.
2026-07-03 사고의 실제 원인이 이거였다 — `langgraph`가 아예 없는 상태로 본 실행을 시도했음.
**중요: 이 import 체크 리스트는 손으로 관리하면 반드시 또 빠진다.** 오늘 `langgraph`를 넣어도
다음 주에 새 패키지를 추가하면서 이 리스트 갱신을 잊으면 똑같은 사고가 난다. 그래서
`requirements.txt`(또는 `pyproject.toml`)의 핵심 의존성을 단일 소스로 삼아 거기서 끌어오거나,
그게 어려우면 최소한 **"새 패키지를 코드에 추가하면 preflight 체크 리스트도 같이 갱신한다"**를
불변 규칙으로 못 박는다. `preflight.py`의 `REQUIRED_IMPORTS` 상단에 이 규칙을 주석으로 남긴다.

**2. venv/경로 체크** — `sys.executable`을 로그에 찍어 "지금 어느 파이썬으로 떠 있는지" 남긴다.
sbatch 스크립트 쪽에서는 `set -euo pipefail` + 명시적 venv 활성화가 짝이 되어야 한다
(활성화 실패해도 다음 줄로 그냥 넘어가 엉뚱한 파이썬으로 도는 걸 막음). 이 클러스터
전용 함정 하나 추가: `LD_LIBRARY_PATH`를 새로 설정할 때 **덮어쓰면 안 되고 항상 앞에
추가**해야 한다(`LD_LIBRARY_PATH="새경로:$LD_LIBRARY_PATH"`) — 덮어쓰면 CUDA 13.0
toolkit의 `libnvrtc.so.13`이 사라져서 torch/triton이 깨진다(`reference-cluster-specs` 참고).

**3. 인자/config 검증** — argparse로 사람이 매번 손으로 타이핑하게 두지 말고, config를
pydantic(`BaseModel`)으로 받는다. 필수값 누락/타입 오류/허용 안 된 값이면 **config를
import하는 시점에 즉시 예외**로 죽는다. STEP6은 `config.py`를 `@dataclass`에서
`pydantic.BaseModel`로 전환하면서 `track`/`device` 필드에 `field_validator`를 추가해
오타(`track="a"`, `device="gpu"` 같은)를 여기서 바로 잡도록 했다.

**4. 경로/환경변수 프리플라이트** — 출력 폴더 쓰기 가능한지, 입력 파일이 실제로 있는지,
필요하면 GPU가 보이는지(`torch.cuda.is_available()`)까지 여기서 확인한다.

**--- 여기까지 통과해야 무거운 모델 로드 ---**

**5. `data[:2]` 스모크 테스트 (출력물 검증까지 포함해야 진짜 스모크 테스트)** — 실제 GPU에
실제 모델을 올린 상태(인터랙티브 셸)에서 전체 데이터가 아니라 2건만 흘려보고 파이프라인
끝까지 통과하는지 확인한다. 로직 버그는 프리플라이트로 못 잡는다 — 실제로 돌려봐야 나온다.
**"에러 없이 통과"만으로는 부족하다.** 2026-07-01 VLM 관찰 0건 버그처럼 exit 0으로 조용히
통과하면서 결과만 텅 비는 게 제일 무섭다(exit code로 안 잡히는 실패). 그래서 스모크 테스트는
반드시 출력물까지 검증한다: 결과 개수가 입력과 맞는지(`len(results) == 2`), 값이 비어있거나
`None`/`NaN`이 아닌지 `assert`로 못 박는다. **assert 한 줄까지가 스모크 테스트다.**

**6. OOM은 인터랙티브 셸에서 실측** — `srun --gres=gpu:2 --pty bash -l` → `ipython` →
`%load_ext autoreload` / `%autoreload 2` → 모델을 딱 한 번만 로드해두고, 코드를 고칠 때마다
재로딩 없이 함수만 다시 호출한다. 터지면 `%debug`로 그 프레임에 바로 들어가 변수를 본다.
이건 방어 코드로 사전에 못 막는다 — "빨리 잡는" 게 현실적 목표다.
**exit 137을 OOM으로 단정하지 말 것**: 137(=128+9, SIGKILL)은 진짜 OOM일 수도, 수동 kill이나
타임아웃성 kill일 수도 있다. 단정하기 전에 `sacct -j <jobid> --format=State,ExitCode,MaxRSS,ReqMem`로
먼저 확인한다 — `MaxRSS`가 `ReqMem`에 근접했으면 OOM이 맞고, 아니면 다른 원인(walltime 초과,
누가 죽였는지 등)을 봐야 한다. OOM이면 커널 로그(`dmesg`)에 `Out of memory` / `oom-killer` 흔적도 남는다.

## 왜 "main() 첫 줄에 체크 함수 호출"만으로는 부족할 수 있는가 (실제 함정)

STEP6의 `main.py`는 원래 파일 최상단(`run()` 함수 밖)에서 `import embedding_utils`,
`from graph import build_graph`를 **무조건** 실행하고 있었다. `graph.py`는 그 안에서
`from langgraph.graph import StateGraph`를 모듈 최상단에서 import한다. 즉 `langgraph`가
없으면 `run()`이 호출되기도 전에, 파일을 import하는 시점에 이미 죽는다 — `run()` 첫 줄에
`run_preflight()`를 넣어도 그 줄에 도달하지도 못했다.

**고친 방법**: `embedding_utils`/`llm_utils`/`graph`의 import를 파일 최상단에서 `run()`
함수 안, `run_preflight()` 호출 **이후**로 옮겼다. 이제 프리플라이트가 실패하면 무거운
모듈은 아예 import 시도조차 안 하고 5초 안에 죽는다. **체크 함수를 어디에 두느냐가 아니라,
무거운 import 자체를 그 체크보다 뒤로 미루는 게 핵심**이다.

**이 패턴의 부작용 하나 (미리 알아둘 것)**: 무거운 import를 함수 안으로 내리면, 파일 최상단에서
그 모듈의 이름이 안 보이기 때문에 (a) 타입 힌트에서 그 타입을 직접 못 쓰고 (b) linter가
"정의되지 않은 이름"이라고 경고할 수 있다. 해결은 `if TYPE_CHECKING:` 가드 안에서 import하고
타입 힌트는 문자열로 쓰는 것(`def run(model: "LlamaModel")`). 런타임에는 함수 안 import가,
정적 분석에는 `TYPE_CHECKING` import가 각각 동작해서 빨간 줄 없이 지연 import를 유지한다.

## 적용 사례: STEP3_전처리 (config에 따라 필요한 패키지가 다를 때)

STEP6은 REQUIRED_MODULES가 고정 리스트였지만, STEP3의 `registry.py`는 컴포넌트마다 여러
backend를 선택할 수 있는 구조다(STT: faster_whisper/openai_whisper, LLM: hf_transformers/vllm 등).
고정 리스트로 체크하면 "지금 안 쓰는 backend의 패키지가 없다"는 오탐이 뜬다(예: vLLM은 이
클러스터에서 근본적으로 불가능해서 일부러 안 깔아뒀는데, 고정 리스트라면 매번 실패로 잡힘).

**해결**: `config.yaml`을 먼저 로드하고(3단계), **실제로 선택된 impl/backend에 필요한 패키지만**
검사한다(`STEP3_전처리/preflight.py`의 `check_config_dependent_imports` 참고) — `llm.backend`가
`hf_transformers`면 `vllm` 미설치는 문제 삼지 않고, `vlm.params.quantization == "nf4"`일 때만
`bitsandbytes`를 요구하는 식. 이렇게 하면 "config가 실제로 쓰는 것 = 검증 대상"이 자동으로
일치해서, 안 쓰는 옵션 때문에 프리플라이트가 헛되이 실패하지 않는다.

**추가로 확인된 것 — STEP3는 이미 지연 import가 잘 돼 있었다**: `import tacit_pipeline`을
실측(`python3 -X importtime`)했더니 0.4초 만에 끝나고 ultralytics/torch/transformers/
faster_whisper 어느 것도 안 끌고 왔다(YOLO/STT/VLM/LLM 어댑터 전부 `_load()` 안에서만 지연
import하도록 이미 설계돼 있었음). 즉 "왜 main() 첫 줄 체크만으로는 부족한가" 문제가 여기선
애초에 없었다 — 코드가 이미 잘 짜여 있으면 프리플라이트를 진입점 맨 앞에 넣는 것만으로 충분하다.
**새 프로젝트를 시작할 때 애초에 이렇게(무거운 import를 `_load()`/`build_*()` 함수 안에만) 짜두면
나중에 프리플라이트를 끼워 넣기 훨씬 쉽다** — 이건 STEP6처럼 나중에 파일을 뜯어고치지 않아도 되는
사전 예방 설계다.

**추가 발견 — `requirements.txt`가 깨져있는 경우**: `00_사전연구/01_STT선정/requirements_v2.txt`가
`-r requirements.txt`로 v1 파일을 참조하는데, 정작 그 v1 `requirements.txt` 파일 자체가 폴더에
없다(과거 정리 중 유실된 것으로 추정). `pip install -r requirements_v2.txt`를 그대로 실행하면
이 지점에서 즉시 실패한다 — **requirements 파일 사이의 참조(`-r`)도 실제로 존재하는지 preflight나
설치 스크립트에서 확인 대상이다.**

  "패키지 없는지 확인하는 코드"가 그 패키지 없어서 죽는 모순을 피함).
- `STEP6_품질검증/config.py` — pydantic BaseModel 전환 예시.
- `STEP6_품질검증/main.py`의 `run()` — `run_preflight()` 호출 후 무거운 import.
- `STEP3_전처리/preflight.py` — config-aware 조건부 체크 예시(`check_config_dependent_imports`).
  `run.py`/`run_all_clips.py` 양쪽 진입점에 연결됨.
- `00_사전연구/preflight.py` — 여러 개의 독립 스크립트(단일 진입점이 없는 연구 코드)에 공용으로
  쓰는 최소 버전. 스크립트 하나하나에 끼워 넣기보다, 실험 스크립트를 돌리기 전에 먼저 한 번
  단독 실행하는 용도(`python3 00_사전연구/preflight.py`).

다른 STEP에 같은 패턴을 적용할 때도 이 순서와 "무거운 import 지연" 원칙을 그대로 따르면 된다.
새로 시작하는 프로젝트는 애초에 무거운 import를 함수 안에 넣어 설계하면 나중에 훨씬 편하다.
