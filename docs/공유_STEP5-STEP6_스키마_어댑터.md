# STEP5→STEP6 스키마 어댑터 도입 — 팀 공유용

**2026-07-08. 대상: STEP6_품질검증(품질검증 단계) 담당자.**

## 발견된 것

STEP5(암묵지 후보 생성)가 실제로 완주해서 만드는 산출물로 STEP6을 계약 감사(코드가
실제로 읽는 키 vs 산출물이 실제로 갖는 키 대조)해봤더니, **STEP6이 지금까지 STEP5의
진짜 산출물로 한 번도 안 돌아가 봤다**는 게 드러났습니다. 구체적으로 3가지 스키마
불일치:

1. **파일 구조**: STEP6은 "JSON 파일 하나 = 후보 하나"를 전제로 코드를 짰습니다
   (`candidate["metadata"]["source"]`를 파일 최상위에서 바로 접근). 실제 STEP5
   출력은 "영상 하나 = 후보 배열"입니다(`{"video_id":..., "candidates":[...]}`,
   클립 하나에서 후보가 여러 건 나옴). 이 구조 그대로 STEP6에 넘기면 파일마다
   `KeyError: 'metadata'`로 즉시 크래시합니다.
2. **transcript 키 이름**: STEP6의 `load_transcript()`는 `{"segments":[{"timestamp",
   "text"}]}` 형식을 기대하는데, STEP3 실제 transcript는 `{"utterances":[{"start"
   (초 단위 숫자), "raw_text"}]}` 입니다. 두 조건 다 안 맞아서 조용히 빈 리스트로
   폴백 — 즉 STEP6의 0단계(발화 실재성 검증)가 사실상 항상 "transcript 없음"으로
   처리되고 있었습니다.
3. **견본 전용 개발**: STEP6이 가진 입력 예시(`input/tk_dell7920_mem_boot_001.json`,
   `input/transcripts/transcript_example.json`)는 사람이 손으로 만든 견본입니다.
   즉 지금까지 STEP6은 이 견본으로만 테스트됐지, STEP5 산출물로는 검증된 적이
   없었습니다.

(참고로 STEP6의 판정 로직 자체와 GT 처리는 문제 없었습니다 — accept/hold/reject
가중치·threshold 로직은 정상이고, 정답지(answer_key) 내용이 판정 경로에 흘러들어가는
지점도 0건이었습니다. 문제는 순전히 입출력 스키마 접합부였습니다.)

## 결정한 것

**STEP6 코드는 한 줄도 수정하지 않습니다.** 대신 STEP5 쪽에 새 어댑터 스크립트
(`STEP5_LLM으로_암묵지_후보생성/step6_adapter.py`)를 추가해서, STEP6이 원래
기대하던 형식으로 미리 변환해줍니다:

- STEP5의 `{candidates:[...]}` 파일을 후보 하나당 개별 JSON 파일로 분리(파일명 =
  후보 id).
- STEP3의 `{utterances:[{start,raw_text}]}`를 STEP6이 기대하는
  `{segments:[{timestamp:"HH:MM:SS", text}]}`로 변환.
- **변환 검증을 어댑터 안에 내장**했습니다 — 발화 건수/원문/시각이 변환 전후로
  정확히 일치하는지 자동으로 대조하고, 하나라도 안 맞으면 예외로 죽습니다(조용히
  넘어가지 않음). 이렇게 안 하면 변환 과정에서 발화가 하나라도 빠지거나 시각이
  어긋났을 때, 멀쩡한 후보가 STEP6 0단계에서 "발화를 지어낸 것"으로 오판정(reject)
  당할 수 있기 때문입니다.
- 산출물은 STEP5 쪽 새 폴더(`STEP5_.../output/step6_adapter_input/`)에만 쓰고,
  STEP6 폴더 자체나 원본 STEP3/STEP5 산출물은 전혀 건드리지 않습니다.

frame_source.py에서 균일추출/모션가이드 두 프레임 소스를 같은 인터페이스로 감싼
것과 동일한 패턴입니다 — "다른 팀 코드는 안 건드리고, 우리 쪽에서 형식을 맞춘다."

## 앞으로

이 어댑터로 모션가이드 4클립 실물 출력을 STEP6에 처음으로 통과시켜 크래시 없이
완주하는지 확인 중입니다(결과는 별도 보고). 장기적으로는 STEP6 쪽에서 직접 STEP5
스키마를 받아들이게 고치는 게 더 깔끔할 수도 있는데, 그건 STEP6 담당자와 상의해서
정하면 될 것 같습니다 — 지금은 어댑터로 급한 불(크래시)부터 끄는 쪽을 택했습니다.

## 추가 발견: 0단계 경계 오탐 패턴 (2026-07-08, CLIP1 실측)

**증상**: CLIP1 후보 12건을 0단계(timestamp_validity)에 통과시켰더니 4건이
"transcript 원문과 불일치"로 FAIL. 그런데 4건 모두 인용한 발화가 transcript에
**원문 그대로 실재**했습니다(윈도우 대조 검사 149건 전수 일치로 별도 증명) —
즉 전부 false reject.

**원인**: 두 코드의 정상 동작이 조합되며 생기는 경계 문제입니다.
1. STT 발화는 빈틈없이 이어지는 경우가 많아, 초 단위 반올림 후
   **앞 세그먼트의 end == 뒤 세그먼트의 start**가 됩니다
   (실측 예: `케이스를 높여서…` 00:00:16~00:00:49, `이 슬롯에 먼저 꽂으면 됩니다`
   00:00:49~00:00:51).
2. STEP6 `rules.py`의 `find_transcript_segment()`는 **경계 포함(start ≤ ts ≤ end)
   조건으로 순회하다 처음 맞는 세그먼트 하나만** 반환합니다. 뒤 발화의 시작 시각
   (위 예시의 49초)을 조회하면 앞 세그먼트가 먼저 잡히고, 이후
   `text_roughly_matches()`가 앞 세그먼트 원문과 비교하니 불일치 → reject.

**조치(적용됨)**: STEP6 무수정 원칙대로 어댑터 쪽에서 완화했습니다 — 변환 시
세그먼트 end를 다음 세그먼트 start-1초로 깎아 겹침 자체를 제거
(step6_adapter.py, 커밋 5cc482b). end는 STEP6이 구간 판정에만 쓰는 값이라
검증 대상(발화 원문·시작 시각)은 그대로입니다. 적용 후 CLIP1 0단계 12/12 통과.

**STEP6 담당자께 — 장기 권장**: 근본적으로는 `find_transcript_segment()`가
최초 매칭 하나가 아니라 **±window(5초) 안의 후보 세그먼트를 전부 모아, 그중
하나라도 원문이 매칭되면 통과**시키는 쪽이 안전합니다. 어댑터 완화는 "겹침"만
없애는 것이라, 시각이 세그먼트 경계에 걸치는 다른 변형(예: 같은 초에 시작하는
두 발화)까지 막아주지는 못합니다. STEP6 코드를 손보게 될 때 반영을 검토해
주세요 — 판정 로직 자체는 건드릴 필요 없고 세그먼트 탐색 함수 하나입니다.
