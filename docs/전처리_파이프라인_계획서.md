# 전처리 파이프라인 계획서 (STEP3)

**목적:** 스마트글래스 작업 영상에서 **암묵지 후보(JSON)** 를 추출하는 전처리 파이프라인의 확정 설계.
**대상:** CLIP1~4 (각 3분 안팎, 총 약 11분)
**이 문서의 위치:** CLI(코드 에이전트)가 그대로 실행할 수 있는 실행 지침. 애매하면 이 문서를 기준으로 판단할 것.

---

## 0. 핵심 원칙 (이걸 어기면 안 됨)

1. **타임스탬프가 절대 기준이다.**
   비디오와 오디오는 **각자 독립적으로** 자기 타임스탬프를 원본 시간축 그대로 유지한다. 어느 한쪽에 억지로 맞추지 않는다. 둘의 유일한 접합점은 **공통 원본 시간축**이다.

2. **암묵지는 세 가지 패턴으로 나온다. 셋 다 놓치면 안 된다.**
   - 행동 O + 발화 X → VLM만 포착 (예: 말없이 손으로 잔열 확인)
   - 행동 X + 발화 O → STT만 포착 (예: 화면 보며 "이건 원래 안 되는 건데")
   - 행동 O + 발화 O → 둘 다 포착, LLM이 연결 (행동+근거)

3. **무음 구간은 비워둔다. 잘라 붙이지 않는다.**
   VAD로 무음을 탐지하되, STT 타임스탬프는 원본 시간축을 유지한다. 무음 구간을 제거해 발화를 앞으로 당기면 비디오와 어긋난다. 무음은 "발화 없음"으로 비워둘 것.

4. **LLM은 입력에 없는 사실을 지어내지 않는다.** (VLM 출력 + STT 출력에 명시된 것만 사용)

## 1. 전체 구조

```
                  mp4 원본
                     │
          ┌──────────┴──────────┐
          │                     │
      [비디오 경로]          [오디오 경로]
          │                     │
   균등 프레임 추출          VAD (무음 탐지)
   (전체 커버, 모션X)            │
          │                  STT (Whisper)
      YOLO 검출                 │  → 원본 타임스탬프 유지
          │                 Transcript 정제
      VLM (행동 추출)            │  → 근거성 발화 추출
          │  → 타임스탬프         │
          └──────────┬──────────┘
                     │
        LLM 암묵지 후보 생성 (융합)
        - 같은 시간대 행동+발화 연결
        - 행동만/발화만도 각각 후보화
                     │
              암묵지 JSON (스키마 v1.3)
```

## 2. 비디오 경로

### 2-1. 프레임 샘플링 — **모션 가이드 샘플링 사용 안 함**

**결정: 0.5fps 균등 추출로 전체를 커버한다. 모션 기반으로 프레임을 잘라내지 않는다.**

**근거 (문서화 필수 — 나중에 "왜 모션 안 썼냐" 질문 대비):**

1. **영상이 짧다.** 클립당 3분 안팎, 총 11분. 모션 샘플링의 존재 이유(긴 영상에서 무의미 구간 제거로 처리량 절감)가 거의 없다. 0.5fps면 클립당 약 55프레임 — 통째로 처리해도 부담이 작다. 모션으로 21% 잘라봤자 아끼는 건 미미하고, 잘못 자르면 암묵지 순간을 잃는 리스크만 커진다.

2. **1인칭 스마트글래스 영상은 모션 변별력이 없다.** 팀원 모션 보고서(2026-07-01)에서 유효 모션 비율이 전 영상 **98~99%**로 측정됨. 머리가 계속 움직여 화면 전체가 항상 흔들리므로 absdiff 모션 스코어가 변별력을 잃는다. "모션 기반"이라면서 사실상 균등 추출과 다르지 않다.

3. **저모션 = 버려도 되는 구간이 아니다.** 1인칭에서 저모션 구간은 작업자가 뭔가를 응시하거나 정밀하게 손대는 순간 — 즉 잡고 싶은 암묵지 순간일 가능성이 높다. 모션 기준 제거는 이걸 버릴 위험이 있다.

**팀원 모션 파이프라인(absdiff 스코어) 활용 방침:**
- 프레임을 **자르는 기준으로는 쓰지 않는다.**
- 모션 스코어는 **motion_classifier(유형 분류) 용도로만** 남긴다 — 어떤 구간이 고모션/정밀작업인지 "라벨"로 활용 가능. (선택 사항, 후순위)

### 2-2. YOLO 검출
- 균등 추출된 프레임 전체에 대해 손/부품 등 객체 검출.
- 결과는 VLM 입력의 보조 정보로 사용.
- **주의:** LLM까지 넘어가는 텍스트가 과다해지지 않도록 검출 결과는 요약/정리해서 전달 (프레임×객체 전부를 raw로 쏟지 말 것 — LLM OOM 원인).

### 2-3. VLM (행동 추출)
- 입력: YOLO 결과 + 프레임. **55프레임 전체가 모델에 반영되는지 반드시 확인.**
- **기지 버그 (이미 원인 파악됨, 재발 방지용 기록):**
  - **버그1 — 프레임 리샘플링:** transformers가 metadata.fps를 24로 오인해 55프레임을 4프레임으로 축소(`video_grid_thw=[[2,30,22]]`). → processor에 **실제 fps(0.5)를 명시**하거나 `do_sample_frames=False`로 리샘플링 차단. 후자보다 실제 fps 명시가 타임스탬프 정확도에 유리.
  - **버그2 — 타임스탬프 강제:** 프레임 시각 55개를 나열하고 "이 중 하나를 정확히 골라라"고 제약하면 모델이 빈 배열(`observations: []`)을 뱉음. → 관찰은 자유롭게 뽑게 하고, 정밀 타임스탬프가 필요하면 **후처리에서 프레임 인덱스↔실제 시각 매핑**으로 붙일 것.
- 출력: 행동(무엇을 했나) + 대략 타임스탬프. 형식 고정 필요.

## 3. 오디오 경로

### 3-1. VAD — **사용 확정** (실험 완료)
- 무음 구간 탐지. **STT 타임스탬프는 원본 시간축 유지, 무음은 비워둠** (원칙 3번).

### 3-2. STT (Whisper)
- 한국어 성능 기준 Whisper 사용. 발화별 타임스탬프 출력.

### 3-3. Transcript 정제
- 영어 단어 변환.
- **근거성 발화 추출** (정규식 또는 LLM 분류기):
  - 인과·조건: "~때문에", "~하면 ~돼", "안 그러면"
  - 매뉴얼과 다른 부분: "원래는 ~인데", "보통은", "사실"
  - 주의: "꼭", "절대", "조심"
  - 부정: "이렇게 하면 안 돼"

## 4. LLM 암묵지 후보 생성 (융합)

- 입력: VLM 행동 출력 + 정제된 STT 출력.
- **융합 = 오디오/비디오 JSON을 나중에 합치는 게 아니라, 같은 시간대의 행동과 근거를 하나의 암묵지 후보로 엮는 것.**
  - 예: VLM "작업 전 손으로 만져본다" + STT "온도 남으면 안 됩니다" → LLM "작업 전 잔열 여부를 촉각으로 확인하는 안전 점검"
- 행동만 있는 구간(발화 X), 발화만 있는 구간(행동 X)도 **각각 독립 후보**로 만든다. 타임스탬프 겹침 여부로 판단.
- **제약:** 입력에 없는 사실 추론·생성 금지. 할루시네이션 방지. 형식은 고정(스키마 v1.3).
- 근거 발화의 timestamp를 JSON에 기록 (`reason_source` / `*_source`).
- 매뉴얼은 이 단계에서 **넣지 않는다** (매뉴얼 내용 재생성 방지). 매뉴얼 대조는 검증 단계에서만.

## 5. 출력: 암묵지 JSON (스키마 v1.3)

**출력은 반드시 아래 구조를 그대로 따른다.** 필드 주석의 `[숫자]`는 값을 채우는 주체(단계) 표기: `[1]`=원본/파일명, `[2]`=STT, `[4]`=LLM/VLM, `[5-1]`=매뉴얼.

```json
{
  "id": "tk_dell7920_mem_boot_001",              // [자동] video_id + task + 일련번호
  "schema_version": "1.3",
  "metadata": {
    "scenario_id": "master_S1_take3",            // [1] 원본 파일명 기반
    "equipment": "Dell Precision 7920",          // [4 LLM] 영상/영상메타에서 식별
    "task": "메모리 부팅 트러블슈팅",              // [4 LLM] 클립에서 작업유형 자동분류
    "keywords": ["부팅 실패", "POST", "RDIMM", "ECC RAM", "LED 패턴", "메모리 슬롯"], // [4 LLM]
    "scenario_title": "조립 후 부팅 실패 진단",    // [4 LLM] 자동 생성
    "source": {
      "video_id": "master_S1_take3.mp4",         // [1] 원본 파일명
      "clip_start": "00:04:12",                  // [2] 시작
      "clip_end":   "00:06:48",                  // [2] 끝
      "transcript_ref": "transcripts/master_S1_take3.json"  // [2 STT] 원문 전체
    }
  },
  "knowledge": {
    "situation": "조립 완료 후 전원은 들어오지만 POST를 통과하지 못하는 상태", // [4 LLM] 적용 상황
    "situation_source": ["00:04:12"],            // [2/4] situation 근거 발화 timestamp
    "tacit_insight": "분해 전에 비파괴 점검(케이블 결선 → 전원 LED 점멸 패턴)을 먼저 읽어 원인 범위를 좁힌다.", // [4 LLM] 한 문장으로 정제된 핵심 노하우
    "reasoning": "LED가 깜빡이는 패턴을 보면 메모리 계열 문제로 원인을 좁힐 수 있다.", // [4 LLM]
    "reasoning_source": ["00:05:02"],            // reasoning의 근거 발화 timestamp
    "reasoning_origin": "utterance",             // utterance | model_inferred
                                                 //   - utterance      : 발화에서 도출
                                                 //   - model_inferred : LLM 일반지식
    "diagnostic_steps": [
      {
        "order": 1,
        "action": "전원·패널 커넥터 등 케이블 전체 결선 확인",  // [4] VLM 행동
        "evidence": "utterance",                             // utterance | action_only
        "source_utterance": "일단 케이블부터 다 다시 꽂아보고", // [2 STT] 원문
        "timestamp": "00:04:30"
      },
      {
        "order": 2,
        "action": "전원 버튼 LED 점멸 패턴 판독 → 원인 범위 좁히기",
        "evidence": "utterance",
        "source_utterance": "여기 불 깜빡이는 거 보면 램 문제예요",
        "timestamp": "00:05:02"
      },
      {
        "order": 3,
        "action": "RDIMM 탈거 후 접점 세척, 재장착",
        "evidence": "utterance",
        "source_utterance": "이거 빼서 접점 닦고 다시 꽂아야",
        "timestamp": "00:05:48"
      },
      {
        "order": 4,
        "action": "슬롯 재배치(권장 채널 순서대로 손에 익은 순서로 재장착)",
        "evidence": "action_only",                           // 행동만 있고 발화 없음
        "source_utterance": null,
        "timestamp": "00:06:10"
      },
      {
        "order": 5,
        "action": "BIOS 진입하여 메모리 인식 검증",
        "evidence": "utterance",
        "source_utterance": "바이오스 들어가서 잡히는지 보고",
        "timestamp": "00:06:30"
      }
    ],
    "conflict": false,                           // [4 LLM] VLM이 본 행동과 STT 발화가 충돌하면 true
    "conflict_detail": null                       // [4 LLM] 충돌 시 내용, 없으면 null
    // "normal_procedure": "CPU0 → 히트싱크 → ECC RDIMM → HDD 캐리어 → SATA0 → 전원·패널 커넥터 → GPU → POST 확인", // [5-1] 매뉴얼 기준 정상절차(델타 판정 기준선). 추출 단계 아님, 검증 단계용.
  }
}
```

**구조 준수 규칙:**
- 위 필드 구조/이름/중첩을 임의로 바꾸지 않는다.
- `evidence`는 `utterance`(발화 근거 있음) 또는 `action_only`(행동만, 발화 없음) 중 하나. `action_only`면 `source_utterance`는 `null`.
- `reasoning_origin`은 `utterance`(발화에서 도출) 또는 `model_inferred`(LLM 일반지식) 중 하나. 원칙 4번(지어내기 금지)에 따라 `model_inferred`는 남발하지 않는다.
- 모든 `*_source` / `timestamp`는 원본 시간축 기준 (원칙 1번).
- `normal_procedure`는 추출 단계에서 채우지 않는다 (매뉴얼 기반, 검증 단계 전용).

## 6. 검증 모드 (지금 당장 이걸로 돌릴 것)

**목표: "이 파이프라인이 효과가 있는지"를 몇 분 안에 확인. 스펙값 고집·OOM 우회 삽질 금지.**

1. **클립 1개만** 돌린다 (전체 배치 X).
2. **max_new_tokens를 낮춘다** (500~1000). OOM 나면 GPU 나누기로 우회하지 말고 이 값부터 줄일 것.
3. 확인 항목:
   - VLM이 55프레임을 실제로 반영하는가 (video_grid_thw의 T 값 확인)
   - VLM 관찰이 비어있지 않고 말이 되는가
   - STT 타임스탬프가 원본 시간축과 맞는가, 무음이 비워졌는가
   - LLM 암묵지 후보가 행동-근거를 제대로 연결하는가
4. 위가 확인되면 그때 max_new_tokens 스펙값 복구 → 전체 배치.

**중지 지시:** 현재 백그라운드로 도는 CLIP3 전체 파이프라인(균등추출+융합, max_new_tokens=4000, GPU 2장 OOM 우회 중)은 위 검증 모드와 다른 방식이므로 **중지하고 검증 모드로 재시작**한다.

**LLM 융합 프롬프트 — 미해결 이슈 (다음 세션 과제):**
검증모드(§6, max_new_tokens 낮춤)로 CLIP3 3회 반복 실행한 결과:
1. 1차: VLM 관찰 11건 정상 생성됐으나, LLM이 이를 전부 무시하고 STT 발화(1:01~1:37)만으로
   diagnostic_steps 5개를 채움. VLM 행동(0~10초)은 situation_source에만 살짝 인용되고
   실제 문장은 반영 안 됨. `evidence="action_only"`인 스텝이 하나도 없었음.
2. 프롬프트에 "[행동 누락 절대 금지]"(발화 누락 금지와 대칭) + "[시간적으로 먼 구간은 별도
   후보로 분리]" 규칙 추가 후 재실행(2차):
   - **부분 개선**: VLM의 실제 관찰 문장이 diagnostic_steps.action에 그대로 들어감(전엔 LLM이
     뭉뚱그려 요약했었음).
   - **새 문제 발생**: 그 VLM 행동들이 `evidence="utterance"`로 잘못 태깅되고, 실제로는
     무관한 시간적으로 가까운 발화("시작합니다." 등)를 `source_utterance`로 갖다 붙임 —
     `action_only`로 남겨야 할 것을 억지로 발화와 엮음.
   - **후보 분리 규칙 무효**: 0초(행동)와 1:01~1:37(발화)이 97초 이상 떨어져 있는데도
     여전히 후보 1개로 합쳐짐. "시간 멀면 분리" 규칙이 안 먹힘.

**결론:** 파이프라인은 end-to-end로 도는 상태(환경 문제 없음)이지만, LLM 융합이 원칙 2번
(행동 O+발화 X 를 action_only로 정직하게 남기기)과 원칙 4번(입력에 없는 연결을 지어내지 않기)을
아직 안정적으로 못 지킴 — 근거 라벨링(evidence 필드)의 정확도가 신뢰 못할 수준. 다음 세션에서
`llm_fusion_prompt.py`를 더 다듬거나(few-shot 예시 추가 등), 또는 evidence 태깅을 LLM 자유
판단이 아니라 코드 레벨 규칙(예: source_utterance가 실제로 그 행동의 ±N초 이내 발화일 때만
evidence=utterance 허용)으로 보강하는 방향을 검토할 것.

**현재 config.yaml 상태(검증모드 값, 스펙값 아님):** `vlm.max_new_tokens=1000`,
`llm.max_new_tokens=1200`. 위 프롬프트 이슈 해결 전까지는 스펙값(4000/2048)으로 복구하지 말 것
— 스펙값 복구는 §6 4번 규칙대로 검증 통과 후에.
